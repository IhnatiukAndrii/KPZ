# Принципи програмування проєкту

У цьому проєкті дотримано ряду фундаментальних принципів розробки програмного забезпечення, що забезпечують його модульність, розширюваність та легкість у підтримці. Нижче наведено опис кожного з них із посиланнями на відповідні файли та рядки коду.

## 1. Single Responsibility Principle (SRP) - Принцип єдиної відповідальності
Кожен клас у проєкті відповідає лише за одну чітко визначену задачу.
- **Логування:** Клас `Logger` ([src/utils/Logger.ts](src/utils/Logger.ts#L1-L17)) має єдину мету — виведення інформації у консоль із відповідним форматуванням. Він не взаємодіє з бізнес-логікою.
- **Робота з файловою системою:** Клас `StorageService` ([src/services/StorageService.ts](src/services/StorageService.ts#L5-L36)) відповідальний винятково за читання та запис даних у файл `data.json`.
- **Бізнес-логіка:** Клас `TaskService` ([src/services/TaskService.ts](src/services/TaskService.ts#L5-L53)) займається лише маніпуляціями із завданнями в пам'яті (додавання, видалення, оновлення статусів), делегуючи збереження до `StorageService`.

## 2. Open/Closed Principle (OCP) - Принцип відкритості/закритості
Програмні сутності повинні бути відкриті для розширення, але закриті для змін.
- **Обробка консольних команд:** Клас `App` використовує мапу для реєстрації команд ([src/app.ts](src/app.ts#L11-L25)). Якщо нам потрібно додати нову команду (наприклад, команду редагування), ми створимо новий спеціалізований клас і просто зареєструємо його, викликавши `registerCommand()`. Оригінальний метод координації `run()` ([src/app.ts](src/app.ts#L27-L44)) при цьому змінювати не доведеться, тобто він надійно захищений від внутрішніх модифікацій.

## 3. Dependency Inversion Principle (DIP) - Принцип інверсії залежностей
Високорівневі модулі не повинні залежати від низькорівневих модулів. Обидва повинні залежати від абстракцій.
- **Абстракція команд:** Головний клас застосунку покладається на інтерфейс `Command` ([src/commands/Command.ts](src/commands/Command.ts#L1-L5)), а не на конкретні реалізації таких класів, як `AddCommand` чи `ListCommand`. Зберігання та виклик команд виконується через інтерфейс-абстракцію (`command.execute(commandArgs)`), що робить `App` незалежним від деталей імплементації самих команд ([src/app.ts](src/app.ts#L36-L39)).
- **Впровадження залежностей (Dependency Injection):** Сервісу завдань `TaskService` передається об'єкт збереження даних безпосередньо через конструктор (впровадження залежностей), що дозволяє легко замінити реалізацію сховища в майбутньому на іншу, наприклад, DatabaseStorage ([src/services/TaskService.ts](src/services/TaskService.ts#L8-L10)).

## 4. DRY (Don't Repeat Yourself) - Не повторюйся
Код уникає дублювання шляхом винесення спільної логіки в окремі класи та методи.
- **Перевірка файлу даних:** Замість того, щоб щоразу перед записом чи читанням файлу перевіряти його існування, це локалізовано в одному приватному методі `ensureFileExists()` класу `StorageService`, який потім використовується під час ініціалізації ([src/services/StorageService.ts](src/services/StorageService.ts#L8-L17)).

## 5. KISS (Keep It Simple, Stupid) - Роби це простіше
Система залишається настільки простою, наскільки це можливо, без надмірно складних архітектурних конструкцій там, де це не є виправданим.
- **Моделі даних:** Замість використання важких ORM-моделей чи класів зі складними гетерами й сетерами, модель сутності `Task` реалізовано як звичайний Typescript-інтерфейс ([src/models/Task.ts](src/models/Task.ts#L7-L14)).
- **Парсинг аргументів:** Замість встановлення потужних сторонніх бібліотек на кшталт `yargs` або `commander` для такого малого проєкту, парсинг аргументів виконано найпростішим шляхом через виклик `slice()` масиву ([src/app.ts](src/app.ts#L34)).
